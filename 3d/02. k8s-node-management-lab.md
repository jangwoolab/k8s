# Kubernetes 노드 관리 실습 가이드 (Hands-on Lab)

> 이 문서는 Kubernetes 관리자가 노드 관리 핵심 작업을 **직접 손으로 따라 하며** 익히는 실습 가이드입니다.
> 각 실습은 `목표 → 실습 명령 → 예상 결과 → 확인 포인트` 순으로 구성됩니다.

---

## 실습 전제 조건

- 동작 중인 Kubernetes 클러스터 (컨트롤 플레인 1대 + 워커 2대 이상 권장)
- `kubectl`이 설정되어 컨트롤 플레인에 접근 가능
- 일부 실습(리소스 모니터링)은 **metrics-server**가 설치되어 있어야 함

예시 노드 구성 (본인 환경에 맞게 치환):

| 역할 | 호스트네임 |
|---|---|
| 컨트롤 플레인 | k8s-cp01 |
| 워커 1 | k8s-worker01 |
| 워커 2 | k8s-worker02 |

> 아래 명령에서 `<노드명>`은 본인 환경의 실제 노드 이름으로 바꿔 실행하세요.

---

# LAB 1. 노드 조회와 상태 진단

**목표**: 노드 목록을 조회하고 상태(Conditions)·용량을 읽는 법을 익힌다.

### 1-1. 노드 목록 조회

```bash
kubectl get nodes
```

예상 결과:

```
NAME           STATUS   ROLES           AGE   VERSION
k8s-cp01       Ready    control-plane   2d    v1.36.x
k8s-worker01   Ready    <none>          2d    v1.36.x
k8s-worker02   Ready    <none>          2d    v1.36.x
```

### 1-2. 상세 정보 조회

```bash
kubectl get nodes -o wide
```

> INTERNAL-IP, OS-IMAGE, KERNEL-VERSION, CONTAINER-RUNTIME 컬럼을 확인합니다.

### 1-3. 노드 상세 분석

```bash
kubectl describe node k8s-worker01
```

**확인 포인트** — 출력에서 다음 섹션을 직접 찾아보세요.
- `Conditions`: `Ready=True`, 나머지 Pressure 계열은 `False`여야 정상
- `Capacity` vs `Allocatable`: 두 값의 차이(시스템 예약분)
- `Taints`: 워커 노드는 보통 `<none>`
- `Non-terminated Pods`: 이 노드에 배치된 파드와 리소스 요청 합계

### 1-4. 특정 노드의 파드 조회

```bash
kubectl get pods -A -o wide --field-selector spec.nodeName=k8s-worker01
```

✅ **체크**: describe 출력에서 `Ready` Condition과 Allocatable 값을 설명할 수 있다.

# LAB 2. 노드 리소스 모니터링

**목표**: 노드별 CPU·메모리 실제 사용량을 확인한다. (metrics-server 필요)

```bash
# 전체 노드 사용량
kubectl top node

# 특정 노드
kubectl top node k8s-worker01
```

예상 결과:

```
NAME           CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
k8s-worker01   145m         7%     1024Mi          27%
```

> `error: Metrics API not available` 가 나오면 metrics-server가 미설치 상태입니다. 

##  metrics-server 설치: 
```bash
`kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml`
```

### 자체 서명 인증서인 경우 아래 명령어 실행
```bash
kubectl patch deployment metrics-server -n kube-system --type='json' \
    -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
```




> (kubeadm 자체 서명 환경에서는 deployment에 `--kubelet-insecure-tls` 인자 추가가 필요할 수 있음)


✅ **체크**: `top node`로 사용량을, `describe node`로 요청(request) 기반 할당량을 구분해 설명할 수 있다.

# LAB 3. 라벨과 nodeSelector로 파드 배치 제어

**목표**: 노드 라벨을 붙이고, 파드를 특정 노드에만 배치한다.

### 3-1. 노드에 라벨 부여

```bash
kubectl label node k8s-worker01 disktype=ssd

# 확인
kubectl get nodes --show-labels | grep disktype
kubectl get nodes -l disktype=ssd
```

### 3-2. nodeSelector로 파드 배치

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: ssd-pod
spec:
  nodeSelector:
    disktype: ssd
  containers:
    - name: nginx
      image: nginx:alpine
EOF
```

### 3-3. 배치 확인

```bash
kubectl get pod ssd-pod -o wide
```

**확인 포인트**: `NODE` 컬럼이 `k8s-worker01`(라벨을 부여한 노드)인지 확인합니다.

### 3-4. 정리

```bash
kubectl delete pod ssd-pod
kubectl label node k8s-worker01 disktype-
```

✅ **체크**: 라벨을 다른 노드(worker02)에 붙이면 파드가 그쪽으로 배치되는지 응용 실험해 본다.

# LAB 4. Cordon / Uncordon (스케줄링 차단)

**목표**: 기존 파드는 유지하면서 새 파드 배치만 막는 동작을 확인한다.

### 4-1. 노드 차단

```bash
kubectl cordon k8s-worker02
kubectl get nodes
```

예상 결과 — STATUS에 `SchedulingDisabled`가 추가됨:

```
NAME           STATUS                     ROLES    AGE   VERSION
k8s-worker02   Ready,SchedulingDisabled   <none>   2d    v1.36.x
```

### 4-2. 새 파드 배치 동작 확인

```bash
# 파드 3개 배포 후, worker02에는 새로 안 뜨는지 확인
kubectl create deployment cordon-test --image=nginx:alpine --replicas=3
kubectl get pods -o wide -l app=cordon-test
```

**확인 포인트**: 새 파드들이 `k8s-worker02`를 제외한 노드에만 배치됩니다. (기존에 있던 파드는 그대로 유지)

### 4-3. 차단 해제 및 정리

```bash
kubectl uncordon k8s-worker02
kubectl get nodes              # SchedulingDisabled 사라짐 확인
kubectl delete deployment cordon-test
```

✅ **체크**: cordon은 "기존 파드 유지 + 새 파드만 차단"임을 직접 관찰했다.

---

# LAB 5. Drain (노드 비우기 / 유지보수)

**목표**: 노드를 안전하게 비우고, 유지보수 후 복귀시키는 표준 워크플로우를 수행한다.

### 5-1. 사전 워크로드 배치

```bash
kubectl create deployment drain-test --image=nginx:alpine --replicas=4
kubectl get pods -o wide -l app=drain-test
```

> worker01에 배치된 파드가 몇 개인지 미리 메모해 둡니다.

### 5-2. 노드 비우기

```bash
kubectl drain k8s-worker01 \
  --ignore-daemonsets \
  --delete-emptydir-data
```

예상 동작:
- 노드가 자동으로 cordon 처리됨
- 해당 노드의 파드가 다른 노드로 이주(재생성)됨
- DaemonSet 파드는 `--ignore-daemonsets` 때문에 그대로 둠

### 5-3. 이주 결과 확인

```bash
kubectl get pods -o wide -l app=drain-test
kubectl get nodes
```

**확인 포인트**: worker01에 있던 `drain-test` 파드들이 다른 노드에서 다시 떠 있고, worker01은 `SchedulingDisabled` 상태입니다.

### 5-4. 유지보수 완료 후 복귀

```bash
# (실제로는 이 시점에 OS 패치 / 재부팅 / 점검 수행)
kubectl uncordon k8s-worker01
kubectl get nodes
```

### 5-5. 정리

```bash
kubectl delete deployment drain-test
```

✅ **체크**: `drain → (작업) → uncordon` 워크플로우를 끝까지 수행했다. `--ignore-daemonsets`가 왜 필요한지 설명할 수 있다.

# LAB 6. Taints & Tolerations (선별적 배치)

**목표**: 노드에 taint를 찍어 특정 파드만 받도록 제어한다.

### 6-1. taint 부여

```bash
kubectl taint nodes k8s-worker02 dedicated=team-a:NoSchedule

# 확인
kubectl describe node k8s-worker02 | grep -i taint
```

### 6-2. toleration 없는 파드 — 배치 안 됨 확인

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: no-tol-pod
spec:
  containers:
    - name: nginx
      image: nginx:alpine
EOF

kubectl get pod no-tol-pod -o wide
```

**확인 포인트**: 파드가 worker02에는 배치되지 않습니다. (다른 노드에 뜨거나, 노드가 worker02뿐이면 Pending)

### 6-3. toleration 있는 파드 — 배치 허용 확인

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: tol-pod
spec:
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "team-a"
      effect: "NoSchedule"
  nodeSelector:
    kubernetes.io/hostname: k8s-worker02
  containers:
    - name: nginx
      image: nginx:alpine
EOF

kubectl get pod tol-pod -o wide
```

**확인 포인트**: `tol-pod`는 toleration을 갖고 있어 worker02에 정상 배치됩니다.

### 6-4. 정리

```bash
kubectl delete pod no-tol-pod tol-pod --ignore-not-found
kubectl taint nodes k8s-worker02 dedicated=team-a:NoSchedule-
```

✅ **체크**: taint(노드가 거부) vs cordon(전체 차단)의 차이를 설명할 수 있다.

# LAB 7. 노드 디버깅

**목표**: 노드 레벨 문제를 진단하는 도구를 사용해 본다.

### 7-1. 디버그 파드로 노드 접근

```bash
kubectl debug node/k8s-worker01 -it --image=busybox
# 컨테이너 내부에서 /host 경로로 노드 파일시스템 접근 가능
# 확인 후 exit
```

### 7-2. 노드에서 직접 확인 (해당 노드에 SSH 접속 후)

```bash
# kubelet 상태 및 로그
systemctl status kubelet
journalctl -u kubelet -f

# 컨테이너 런타임(containerd) 상태
sudo crictl ps          # 실행 중인 컨테이너
sudo crictl pods        # 파드 샌드박스
```

✅ **체크**: 노드 NotReady 시 가장 먼저 볼 곳(kubelet 로그, 런타임 상태)을 안다.

# LAB 8. (선택) 노드 클러스터에서 제거

> 실습 환경을 망가뜨릴 수 있으니, 다시 복구 가능한 환경에서만 수행하세요.

```bash
# 1) 비우기
kubectl drain k8s-worker02 --ignore-daemonsets --delete-emptydir-data

# 2) 클러스터에서 삭제
kubectl delete node k8s-worker02

# 3) 해당 노드(worker02)에서 kubeadm 초기화
sudo kubeadm reset -f
sudo rm -rf /etc/cni/net.d

# 4) 재가입하려면 컨트롤 플레인에서 join 명령 생성
```

## 핵심 개념 정리 (실습 후 복습)

| 작업 | 동작 | 대표 명령 |
|---|---|---|
| cordon | 새 파드만 차단, 기존 유지 | `kubectl cordon` |
| drain | cordon + 기존 파드 이주 | `kubectl drain --ignore-daemonsets` |
| uncordon | 스케줄링 재허용 | `kubectl uncordon` |
| label | 노드 분류·선택 기준 부여 | `kubectl label node` |
| taint | 특정 파드만 선별 허용/배제 | `kubectl taint nodes` |
| 진단 | 상태·용량·이벤트 확인 | `kubectl describe node` |
| 모니터링 | 실제 자원 사용량 | `kubectl top node` |
