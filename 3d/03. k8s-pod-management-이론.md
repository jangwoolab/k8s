# Pod 관리 - 이론 및 핵심 명령어

Kubernetes 운영자가 Pod 관리에서 반드시 알아야 할 이론과 실무 명령어를 정리했습니다. 강의 자료 및 현장 레퍼런스로 바로 쓸 수 있도록 개념과 명령을 함께 담았습니다.

---

## 1. Pod란 무엇인가 (이론)

Pod는 Kubernetes에서 **배포·실행의 최소 단위**입니다. 컨테이너를 직접 배포하지 않고, 하나 이상의 컨테이너를 감싼 Pod 단위로 배포합니다.

- 한 Pod 안의 컨테이너들은 **같은 노드에서 함께 실행**되며, **네트워크(IP·포트)와 스토리지(볼륨)를 공유**합니다.
- Pod 내부 컨테이너끼리는 `localhost`로 통신할 수 있습니다.
- Pod는 고유한 **클러스터 내부 IP**를 가지며, Pod가 재생성되면 IP가 바뀝니다. (그래서 안정적 접근에는 Service가 필요)

핵심 성질: **Pod는 일회용(ephemeral)이며 가축(cattle)처럼 다뤄집니다.** 죽으면 고치는 게 아니라 새 Pod로 교체됩니다. 이 때문에 운영자는 개별 Pod보다 이를 관리하는 컨트롤러(Deployment 등)를 다룹니다.

## 2. Pod 구조와 패턴 (이론)

**단일 컨테이너 Pod**가 가장 흔하지만, 하나의 Pod에 여러 컨테이너를 두는 패턴도 있습니다.

- **사이드카(sidecar)**: 메인 컨테이너를 보조 (로그 수집, 프록시 등). 메인과 수명을 함께함
- **init container**: 메인 컨테이너 **시작 전에** 순차 실행되어 초기화 작업 수행 (완료돼야 메인 시작)
- **pause 컨테이너**: 사용자가 직접 다루지 않는 내부 컨테이너로, Pod의 네트워크 네임스페이스를 잡아주는 역할

> 멀티 컨테이너는 "긴밀히 결합되어 반드시 함께 떠야 하는" 경우에만 씁니다. 단순히 두 서비스를 묶는 용도가 아닙니다.

## 3. Pod 라이프사이클 (이론 + 운영 핵심)

### Pod Phase (전체 상태)

| Phase | 의미 |
|---|---|
| `Pending` | 스케줄 대기 또는 이미지 다운로드 중 (아직 컨테이너 미실행) |
| `Running` | 노드에 배치되어 최소 1개 컨테이너가 실행 중 |
| `Succeeded` | 모든 컨테이너가 정상 종료 (Job 등) |
| `Failed` | 모든 컨테이너 종료, 하나 이상 비정상 종료 |
| `Unknown` | 노드 통신 불가 등으로 상태 파악 불가 |

### 컨테이너 상태 (Container State)

`Waiting`(대기/오류 대기), `Running`(실행 중), `Terminated`(종료)로 나뉘며, `describe pod`의 컨테이너 섹션에서 **이유(Reason)**와 함께 확인합니다. (예: Waiting - CrashLoopBackOff)

### restartPolicy (재시작 정책)

- `Always`(기본): 컨테이너가 죽으면 항상 재시작 (Deployment의 Pod)
- `OnFailure`: 비정상 종료 시에만 재시작 (Job)
- `Never`: 재시작 안 함

## 4. 헬스체크 — Probe (이론 + 운영 핵심)

kubelet이 컨테이너 상태를 판단하는 3가지 진단입니다. 운영 안정성의 핵심입니다.

| Probe | 목적 | 실패 시 |
|---|---|---|
| `livenessProbe` | 컨테이너가 살아있는가 | 컨테이너를 **재시작** |
| `readinessProbe` | 트래픽을 받을 준비가 됐는가 | Service **엔드포인트에서 제외** (재시작 안 함) |
| `startupProbe` | 느린 시작 앱이 다 떴는가 | 시작 완료 전까지 liveness·readiness를 **보류** |

진단 방식은 `httpGet`, `tcpSocket`, `exec`(명령 실행) 세 가지입니다.

> 운영 포인트: liveness를 너무 공격적으로 잡으면 정상 앱이 반복 재시작될 수 있습니다. readiness가 빠져 있으면 준비 안 된 Pod로 트래픽이 흘러갑니다.

## 5. 리소스 관리 — requests / limits (이론 + 운영 핵심)

- **requests**: 컨테이너가 **보장받는 최소 자원**. 스케줄러가 이 값을 기준으로 Pod를 노드에 배치합니다.
- **limits**: 컨테이너가 **쓸 수 있는 최대 자원**. CPU는 초과 시 스로틀링(throttle), 메모리는 초과 시 **OOMKilled**(종료)됩니다.

### QoS 클래스 (자원 압박 시 축출 우선순위)

| QoS | 조건 | 축출(eviction) 우선순위 |
|---|---|---|
| `Guaranteed` | 모든 컨테이너의 requests = limits | 가장 나중 (안전) |
| `Burstable` | requests < limits (일부만 설정) | 중간 |
| `BestEffort` | requests·limits 미설정 | 가장 먼저 (위험) |

> 운영 포인트: 중요한 워크로드일수록 requests·limits를 명시해 Guaranteed/Burstable로 두는 것이 안전합니다.

## 6. Pod 배치에 영향을 주는 요소 (이론, 노드 관리와 연결)

Pod가 어느 노드에 뜨는지는 다음으로 제어합니다. (자세한 동작은 노드 관리편 참조)

- **nodeSelector / node affinity**: 파드가 특정 노드를 선택
- **taint / toleration**: 노드가 특정 파드만 허용
- **pod affinity / anti-affinity**: 다른 파드와 같이/떨어져 배치
- **topologySpreadConstraints**: 여러 노드·존에 고르게 분산

## 7. 운영 관점 — Pod를 직접 만들지 않는다

운영 환경에서 Pod는 거의 항상 **컨트롤러를 통해** 생성·관리됩니다.

- **Deployment**: 무상태 앱 (대부분의 경우)
- **StatefulSet**: 상태 저장 앱 (DB 등)
- **DaemonSet**: 모든 노드에 한 개씩 (로그/모니터링 에이전트)
- **Job / CronJob**: 일회성/주기성 작업

> 직접 만든(naked) Pod는 노드 장애 시 재생성되지 않습니다. 운영에서는 항상 컨트롤러를 통해 관리합니다.

## Pod 관리 명령어

### 조회 / 진단

```bash
# 파드 목록 (현재 네임스페이스)
kubectl get pods

# 모든 네임스페이스 + 상세(노드/IP)
kubectl get pods -A -o wide

# 상태 변화를 실시간 관찰
kubectl get pods -w

# 라벨 셀렉터로 필터
kubectl get pods -l app=nginx

# 특정 파드 상세 — 이벤트, 컨테이너 상태, probe, 리소스
kubectl describe pod <파드명>

# YAML 전체 정의 확인
kubectl get pod <파드명> -o yaml

# 리소스 사용량 (metrics-server 필요)
kubectl top pod
kubectl top pod <파드명> --containers
```

### 로그 (운영 핵심)

```bash
# 파드 로그
kubectl logs <파드명>

# 실시간 추적
kubectl logs -f <파드명>

# 멀티 컨테이너 파드에서 특정 컨테이너 지정
kubectl logs <파드명> -c <컨테이너명>

# 직전(재시작 전) 컨테이너의 로그 — CrashLoop 원인 추적에 필수
kubectl logs <파드명> --previous

# 라벨로 여러 파드 로그 한 번에
kubectl logs -l app=nginx --tail=100
```

### 실행 / 접속

```bash
# 파드 안에서 명령 실행 (셸 진입)
kubectl exec -it <파드명> -- /bin/sh
kubectl exec -it <파드명> -c <컨테이너명> -- bash

# 단일 명령 실행
kubectl exec <파드명> -- ls /app

# 로컬 포트를 파드로 포워딩 (디버깅·접속)
kubectl port-forward pod/<파드명> 8080:80

# 파일 복사 (로컬 <-> 파드)
kubectl cp <파드명>:/path/in/pod ./local
kubectl cp ./local <파드명>:/path/in/pod
```

### 디버깅

```bash
# 이벤트 확인 (스케줄 실패·이미지 오류 등 원인)
kubectl get events --sort-by=.lastTimestamp
kubectl describe pod <파드명>      # 하단 Events 섹션

# 임시 디버그 컨테이너를 실행 중인 파드에 주입 (도구 없는 이미지 진단)
kubectl debug <파드명> -it --image=busybox --target=<컨테이너명>

# 문제 파드를 복제해 명령/이미지를 바꿔 디버깅
kubectl debug <파드명> -it --image=busybox --copy-to=<디버그파드명>
```

### 생성 / 삭제

```bash
# 임시 파드 빠르게 실행 (테스트용)
kubectl run testpod --image=nginx:alpine

# 일회성 대화형 파드 (종료 시 삭제)
kubectl run tmp --image=busybox -it --rm -- sh

# 매니페스트로 생성/적용
kubectl apply -f pod.yaml

# 삭제
kubectl delete pod <파드명>

# 즉시 강제 삭제 (Terminating에서 멈춘 경우, 주의해서 사용)
kubectl delete pod <파드명> --force --grace-period=0

# YAML 미리 생성 (dry-run)
kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml
```

## 자주 겪는 문제 (트러블슈팅)

운영에서 가장 자주 만나는 Pod 상태와 원인·조치입니다.

| 상태 / 증상 | 원인 | 조치 |
|---|---|---|
| `Pending` | 스케줄 불가 (자원 부족, taint, nodeSelector 불일치) | `describe pod`의 Events 확인, 노드 자원·taint 점검 |
| `ImagePullBackOff` / `ErrImagePull` | 이미지 이름 오타, 레지스트리 인증 실패 | 이미지 경로·태그 확인, imagePullSecret 점검 |
| `CrashLoopBackOff` | 컨테이너가 계속 죽고 재시작 반복 | `logs --previous`로 죽는 이유 확인, 명령/설정/probe 점검 |
| `OOMKilled` | 메모리 limit 초과로 종료 | 메모리 limit 상향 또는 앱 메모리 사용 점검 |
| `Evicted` | 노드 자원 압박으로 축출 | 노드 자원 확보, requests 설정, QoS 상향 |
| `ContainerCreating` 지속 | 볼륨 마운트 실패, CNI/시크릿 문제 | Events 확인, PVC·Secret·네트워크 점검 |
| `Running` 인데 트래픽 안 옴 | readinessProbe 실패로 엔드포인트 제외 | `describe`로 readiness 상태·Service 셀렉터 확인 |

## 표준 디버깅 워크플로우 (정리)

문제 Pod를 만났을 때의 전형적인 진단 순서입니다.

```bash
# 1) 전체 상태와 재시작 횟수 파악
kubectl get pods -o wide          # STATUS, RESTARTS 확인

# 2) 상세 + 이벤트로 원인 좁히기
kubectl describe pod <파드명>      # Events / 컨테이너 State·Reason

# 3) 로그로 애플리케이션 오류 확인
kubectl logs <파드명>
kubectl logs <파드명> --previous  # 재시작 전 로그 (CrashLoop)

# 4) 필요 시 내부 진입 또는 디버그 컨테이너
kubectl exec -it <파드명> -- sh
kubectl debug <파드명> -it --image=busybox
```

`get → describe(Events) → logs(--previous) → exec/debug` 순서와 Phase·QoS·Probe의 의미만 확실히 잡으면 Pod 운영·트러블슈팅의 대부분을 커버할 수 있습니다.
