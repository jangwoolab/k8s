# Kubernetes Pod 관리 실습 가이드 (Hands-on Lab)

> 이 문서는 Kubernetes 운영자가 Pod 관리 핵심 작업을 **직접 손으로 따라 하며** 익히는 실습 가이드입니다.
> 각 실습은 `목표 → 실습 명령 → 예상 결과 → 확인 포인트` 순으로 구성됩니다.

---

## 실습 전제 조건

- 동작 중인 Kubernetes 클러스터 (컨트롤 플레인 1대 + 워커 1대 이상)
- `kubectl`이 설정되어 클러스터에 접근 가능
- 일부 실습(리소스 모니터링)은 **metrics-server**가 설치되어 있어야 함

> 실습은 전용 네임스페이스에서 진행하면 정리가 편합니다.

```bash
kubectl create namespace pod-lab
kubectl config set-context --current --namespace=pod-lab
```

> 모든 실습이 끝나면 `kubectl delete namespace pod-lab` 한 번으로 정리할 수 있습니다.

# LAB 1. Pod 생성과 조회

**목표**: Pod를 만들고 상태·상세 정보를 읽는 기본기를 익힌다.

### 1-1. Pod 빠르게 생성

```bash
kubectl run web --image=nginx:alpine
```

### 1-2. 상태 조회

```bash
kubectl get pods
kubectl get pods -o wide          # 노드, Pod IP 포함
```

예상 결과:

```
NAME   READY   STATUS    RESTARTS   AGE
web    1/1     Running   0          20s
```

### 1-3. 상세 분석

```bash
kubectl describe pod web
```

**확인 포인트** — 출력에서 다음을 찾아보세요.
- `Status`: Running / `IP`: Pod IP / `Node`: 배치된 노드
- `Containers`: 이미지, 상태(State), 재시작 횟수
- 하단 `Events`: 스케줄 → 이미지 풀 → 시작 순서

### 1-4. YAML 정의 확인

```bash
kubectl get pod web -o yaml | less
```

✅ **체크**: `get pods`의 READY(1/1)와 STATUS의 의미, describe의 Events를 설명할 수 있다.

### 정리

```bash
kubectl delete pod web
```

# LAB 2. Pod 로그 확인

**목표**: 로그로 애플리케이션 동작·오류를 추적한다.

### 2-1. 로그 출력 대상 Pod 생성

```bash
kubectl run logger --image=busybox -- /bin/sh -c \
  "i=0; while true; do echo \"log line \$i\"; i=\$((i+1)); sleep 2; done"
```

### 2-2. 로그 조회

```bash
kubectl logs logger              # 전체 로그
kubectl logs -f logger           # 실시간 추적 (Ctrl+C로 종료)
kubectl logs logger --tail=5     # 마지막 5줄
```

예상 결과:

```
log line 0
log line 1
log line 2
...
```

**확인 포인트**: `-f`로 새 로그가 실시간으로 흐르는지 확인합니다.

> 멀티 컨테이너 Pod라면 `-c <컨테이너명>`으로 대상을 지정하고, 재시작 전 로그는 `--previous`로 봅니다. (LAB 4에서 활용)

✅ **체크**: `-f`, `--tail`, `--previous`, `-c`의 용도를 구분할 수 있다.

### 정리

```bash
kubectl delete pod logger
```

# LAB 3. Pod 내부 접속과 실행

**목표**: 실행 중인 Pod에 접속해 명령을 실행하고 포트를 포워딩한다.

### 3-1. 셸 진입

```bash
kubectl run shell-demo --image=nginx:alpine
kubectl exec -it shell-demo -- /bin/sh

# (컨테이너 내부에서)
ls /usr/share/nginx/html
cat /etc/nginx/nginx.conf
exit
```

### 3-2. 단일 명령 실행

```bash
kubectl exec shell-demo -- nginx -v
```

### 3-3. 포트 포워딩으로 접속

```bash
# 로컬 8080 -> Pod 80
kubectl port-forward pod/shell-demo 8080:80
# (다른 터미널에서)
curl http://localhost:8080
```

**확인 포인트**: 로컬에서 curl 응답으로 nginx 기본 페이지가 오면 성공입니다.

### 3-4. 파일 복사

```bash
echo "hello" > test.txt
kubectl cp test.txt shell-demo:/tmp/test.txt
kubectl exec shell-demo -- cat /tmp/test.txt
```

✅ **체크**: exec(-it), port-forward, cp의 차이와 용도를 설명할 수 있다.

### 정리

```bash
kubectl delete pod shell-demo
rm -f test.txt
```

# LAB 4. 라이프사이클 & CrashLoopBackOff 관찰

**목표**: Pod Phase와 재시작 동작을 직접 관찰하고, CrashLoop 원인을 추적한다.

### 4-1. 즉시 종료되는(실패하는) 컨테이너 생성

```bash
kubectl run crasher --image=busybox -- /bin/sh -c "echo start; sleep 3; exit 1"
```

### 4-2. 재시작 반복 관찰

```bash
kubectl get pods -w        # RESTARTS 증가, STATUS가 CrashLoopBackOff로
```

예상 결과:

```
NAME      READY   STATUS             RESTARTS      AGE
crasher   0/1     CrashLoopBackOff   3 (20s ago)   90s
```

### 4-3. 원인 추적 (핵심)

```bash
kubectl describe pod crasher          # State/Reason, Events 확인
kubectl logs crasher --previous       # 재시작 전 컨테이너 로그
```

**확인 포인트**: `--previous`로 죽기 직전 로그("start")를 확인하고, 종료 코드(Exit Code 1)와 CrashLoopBackOff의 관계를 이해합니다.

✅ **체크**: CrashLoopBackOff를 만나면 `describe` → `logs --previous` 순으로 원인을 찾을 수 있다.

### 정리

```bash
kubectl delete pod crasher
```

# LAB 5. Probe (liveness / readiness) 동작 비교

**목표**: liveness 실패는 재시작, readiness 실패는 트래픽 제외임을 직접 관찰한다.

### 5-1. liveness probe 실패 Pod 생성

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: live-demo
spec:
  containers:
    - name: app
      image: busybox
      args: ["/bin/sh", "-c", "touch /tmp/healthy; sleep 30; rm /tmp/healthy; sleep 600"]
      livenessProbe:
        exec:
          command: ["cat", "/tmp/healthy"]
        initialDelaySeconds: 5
        periodSeconds: 5
EOF
```

### 5-2. 재시작 관찰

```bash
kubectl get pod live-demo -w
# 30초 후 /tmp/healthy 삭제 -> liveness 실패 -> 컨테이너 재시작(RESTARTS 증가)
kubectl describe pod live-demo | grep -A5 Liveness
```

**확인 포인트**: 30초 뒤 liveness가 실패하며 컨테이너가 **재시작**됩니다. Events에 `Liveness probe failed`가 보입니다.

### 5-3. (참고) readiness 차이

readinessProbe가 실패하면 컨테이너는 **재시작되지 않고**, 대신 Service 엔드포인트에서 제외되어 트래픽을 받지 않습니다. `kubectl get endpoints <서비스명>`으로 해당 Pod IP가 빠지는 것을 확인할 수 있습니다.

✅ **체크**: liveness(재시작) vs readiness(트래픽 제외)의 차이를 설명할 수 있다.

### 정리

```bash
kubectl delete pod live-demo
```

# LAB 6. 리소스 requests/limits & QoS

**목표**: 리소스 설정에 따른 QoS 클래스와 메모리 초과(OOMKilled)를 관찰한다.

### 6-1. requests=limits 인 Pod (Guaranteed)

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: qos-demo
spec:
  containers:
    - name: app
      image: nginx:alpine
      resources:
        requests:
          cpu: "100m"
          memory: "64Mi"
        limits:
          cpu: "100m"
          memory: "64Mi"
EOF

kubectl get pod qos-demo -o jsonpath='{.status.qosClass}'; echo
```

**확인 포인트**: 출력이 `Guaranteed` 입니다. (requests=limits)

### 6-2. 메모리 limit 초과 → OOMKilled 관찰

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: oom-demo
spec:
  containers:
    - name: hog
      image: polinux/stress
      command: ["stress"]
      args: ["--vm", "1", "--vm-bytes", "200M", "--vm-hang", "1"]
      resources:
        limits:
          memory: "50Mi"
EOF

kubectl get pod oom-demo -w
kubectl describe pod oom-demo | grep -i -A2 "Last State"
```

**확인 포인트**: 메모리 limit(50Mi)을 초과해 컨테이너가 `OOMKilled`로 종료됩니다. (이미지 풀이 차단된 환경이면 이 단계는 건너뜁니다.)

✅ **체크**: QoS 3등급(Guaranteed/Burstable/BestEffort)과 limit 초과 시 메모리=OOMKilled, CPU=스로틀링을 구분할 수 있다.

### 정리

```bash
kubectl delete pod qos-demo oom-demo --ignore-not-found
```

# LAB 7. 디버깅 & 트러블슈팅 재현

**목표**: 흔한 오류(ImagePullBackOff)를 재현하고 진단 도구를 사용한다.

### 7-1. 이미지 오류 재현 (ImagePullBackOff)

```bash
kubectl run badimage --image=nginx:doesnotexist-tag
kubectl get pods
# STATUS: ErrImagePull -> ImagePullBackOff
```

### 7-2. 원인 진단

```bash
kubectl describe pod badimage | tail -20   # Events에서 풀 실패 사유 확인
kubectl get events --sort-by=.lastTimestamp | tail -10
```

**확인 포인트**: Events에 `Failed to pull image ... not found` 가 보입니다. 이미지 이름·태그가 원인임을 확인합니다.

### 7-3. 디버그 컨테이너로 진단 (도구 없는 이미지)

```bash
# 정상 파드 생성 후, busybox 도구를 임시 주입
kubectl run quiet --image=nginx:alpine
kubectl debug quiet -it --image=busybox --target=quiet -- sh
# (내부에서) wget -qO- localhost:80 등으로 진단 후 exit
```

✅ **체크**: 오류 진단 순서(`get` → `describe`/`events` → `logs`/`debug`)를 적용할 수 있다.

### 정리

```bash
kubectl delete pod badimage quiet --ignore-not-found
```

# LAB 8. 멀티 컨테이너 & init container

**목표**: init container의 순차 실행과 멀티 컨테이너 로그 분리를 관찰한다.

### 8-1. init container + 메인 컨테이너

```bash
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: multi-demo
spec:
  initContainers:
    - name: init-wait
      image: busybox
      command: ["sh", "-c", "echo init 작업 수행; sleep 5"]
  containers:
    - name: main
      image: nginx:alpine
EOF
```

### 8-2. 순차 실행 관찰

```bash
kubectl get pod multi-demo -w
# STATUS: Init:0/1 -> PodInitializing -> Running
```

**확인 포인트**: init container가 끝난 **후에야** 메인 컨테이너가 시작됩니다.

### 8-3. 컨테이너별 로그 분리

```bash
kubectl logs multi-demo -c init-wait      # init 로그
kubectl logs multi-demo -c main           # 메인 로그
```

✅ **체크**: init container의 순차 실행과 `-c`로 컨테이너별 로그를 분리하는 법을 안다.

### 정리

```bash
kubectl delete pod multi-demo
```

## 핵심 개념 정리 (실습 후 복습)

| 작업 | 동작 | 대표 명령 |
|---|---|---|
| 조회 | 상태·노드·IP 확인 | `kubectl get pods -o wide` |
| 진단 | 이벤트·컨테이너 상태 | `kubectl describe pod` |
| 로그 | 앱 로그 / 재시작 전 로그 | `kubectl logs (--previous)` |
| 접속 | 셸 진입 / 명령 실행 | `kubectl exec -it` |
| 포워딩 | 로컬에서 Pod 접속 | `kubectl port-forward` |
| 디버깅 | 임시 컨테이너 주입 | `kubectl debug` |
| 모니터링 | 실제 자원 사용량 | `kubectl top pod` |

| 흔한 상태 | 의미 | 1차 조치 |
|---|---|---|
| `CrashLoopBackOff` | 계속 죽고 재시작 | `logs --previous` |
| `ImagePullBackOff` | 이미지 풀 실패 | 이미지명·태그·인증 확인 |
| `Pending` | 스케줄 불가 | `describe` Events / 노드 자원·taint |
| `OOMKilled` | 메모리 limit 초과 | limit 상향 / 메모리 점검 |

`get → describe(Events) → logs(--previous) → exec/debug` 흐름과 Phase·Probe·QoS의 의미만 확실히 잡으면 Pod 운영·트러블슈팅의 대부분을 커버할 수 있습니다.
