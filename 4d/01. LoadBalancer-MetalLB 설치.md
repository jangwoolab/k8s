## MetalLB란

베어메탈(온프레미스) Kubernetes 클러스터에서 `LoadBalancer` 타입 서비스에 실제 외부 IP를 할당해주는 컨트롤러입니다. 클라우드(AWS/GCP 등)에서는 클라우드 프로바이더가 자동으로 로드밸런서를 만들어주지만, 온프레미스/베어메탈에는 그게 없어서 `LoadBalancer` 서비스가 영원히 `<pending>` 상태로 남는데, 이걸 해결해줍니다.

## [참고] 사전 요구사항
- [**기본은 kube-proxy가 iptables 모드 임**]
- **[참고사항]** kube-proxy가 IPVS 모드면 strict ARP를 켜야 함 (L2 모드 사용 시):

```bash
## 참고 사항임. [kube-proxy가 IPVS 모드면 strict ARP를 켬], 주의: 아래 명령어는 1라인 임.

kubectl get configmap kube-proxy -n kube-system -o yaml | \
sed -e "s/strictARP: false/strictARP: true/" | \
kubectl apply -f - -n kube-system
```

- L2 모드는 Calico 등 일부 CNI와 충돌 가능 (호환성 문서 확인 필요)

# kube-proxy Mode 확인 
kube-proxy가 iptables 모드인지 IPVS 모드인지 확인하는 방법입니다. (MetalLB L2 모드 쓰려면 strictARP 설정 때문에 이걸 먼저 알아야 합니다.)

## 방법 1: ConfigMap에서 확인 (가장 확실함)

```bash
kubectl get configmap kube-proxy -n kube-system -o yaml | grep mode
```

출력이 `mode: ""` 이면 기본값인 **iptables**, `mode: "ipvs"` 이면 **IPVS**입니다.

## 방법 2: 로그에서 확인

```bash
kubectl get pods -n kube-system | grep kube-proxy
```
```bash
kubectl logs <kube-proxy-pod-이름> -n kube-system | grep -i "proxy mode\|using ipvs\|using iptables"
```

## 방법 3: 노드에서 직접 확인

```bash
ssh k8s-cp01

# ipvs 모드면 ipvsadm 규칙이 보임 <==> 안보임
sudo ipvsadm -Ln

# iptables 모드면 KUBE- 로 시작하는 체인이 많이 보임   <==> 보임
sudo iptables -t nat -L | grep KUBE
```

`ipvsadm` 명령이 없으면 `sudo dnf install -y ipvsadm` 후 확인하면 됩니다.

## [참고] - strictARP 켜는 법 (MetalLB L2 모드 쓸 경우)

IPVS 모드로 확인됐다면:

```bash
kubectl get configmap kube-proxy -n kube-system -o yaml | \
sed -e "s/strictARP: false/strictARP: true/" | \
kubectl apply -f - -n kube-system
```

iptables 모드라면 strictARP 설정이 필요 없습니다(기본적으로 문제없이 동작).

## 사용법: IP 풀 설정

설치만으로는 대기 상태입니다. `IPAddressPool`과 광고 방식(L2 또는 BGP)을 CRD로 정의해야 합니다.

**L2 모드 (가장 간단, ARP/NDP로 광고)**
```bash
vi ipaddresspool-metallb.yml
```

```yaml
# ipaddresspool-metallb.yml
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: default-pool
  namespace: metallb-system
spec:
  addresses:
  #- 192.168.1.240-192.168.1.250
  - 10.10.10.50-10.10.10.99
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: l2-adv
  namespace: metallb-system
spec:
  ipAddressPools:
  - default-pool
```

```bash
kubectl apply -f pool.yaml
```

- **확인** 
```bash
kubectl get ipaddresspool -n metallb-system
```

**[참고] - BGP 모드 (라우터가 BGP 지원할 때, 진짜 로드밸런싱 가능)**

```yaml
apiVersion: metallb.io/v1beta1
kind: BGPPeer
metadata:
  name: my-router
  namespace: metallb-system
spec:
  myASN: 64500
  peerASN: 64501
  peerAddress: 192.168.1.1
---
apiVersion: metallb.io/v1beta1
kind: BGPAdvertisement
metadata:
  name: bgp-adv
  namespace: metallb-system
spec:
  ipAddressPools:
  - default-pool
```

## 서비스에서 사용
**[예시:참고]**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  type: LoadBalancer
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 8080
```

```bash
kubectl apply -f svc.yaml
kubectl get svc my-app   # EXTERNAL-IP에 풀에서 할당된 IP가 표시됨
```

특정 IP를 지정하고 싶으면 `spec.loadBalancerIP` (구버전) 또는 `metallb.io/loadBalancerIPs` 어노테이션을, 특정 풀을 지정하려면 `metallb.io/address-pool` 어노테이션을 서비스에 붙이면 됩니다.

L2 모드는 설정이 쉽지만 단일 노드로 트래픽이 몰리는 한계가 있고, BGP 모드는 라우터 설정이 필요한 대신 진짜 로드밸런싱과 페일오버를 제공합니다. 소규모 홈랩/테스트 환경이면 L2로 충분합니다.

# 참고 

## kube-proxy란

각 노드에서 실행되며, Kubernetes Service의 ClusterIP/NodePort/LoadBalancer로 들어온 트래픽을 실제 Pod로 라우팅해주는 컴포넌트입니다. Service ↔ Pod 매핑(엔드포인트)이 바뀔 때마다 이 규칙을 갱신합니다.

## 1. iptables 모드 (기본값)

**동작 방식**: Service/Endpoint 변경사항을 감지할 때마다 리눅스 `iptables`의 NAT 테이블에 규칙을 새로 씁니다. 트래픽은 커널의 netfilter 체인을 순차적으로 통과하며 목적지 Pod로 DNAT 됩니다.

**특징**
- 커널 레벨에서 처리되어 userspace 모드보다 빠름
- 규칙이 **순차 매칭(linear search)** 구조라, Service/엔드포인트 수가 많아지면 규칙 체인이 길어지고 성능이 선형적으로 나빠짐 (수천 개 Service 규모에서 체감)
- 로드밸런싱은 랜덤(확률 기반) 방식만 지원 — 세밀한 알고리즘 선택 불가
- 별도 설정 없이 그냥 되는 가장 무난한 기본 옵션

**적합한 환경**: 중소규모 클러스터, Service 수가 수백 개 이하

## 2. IPVS 모드 - 1.35부터 deprecated  <=>[대안] : nftables 모드

**동작 방식**: 커널의 IPVS(IP Virtual Server) — 원래 L4 로드밸런서 기술 — 를 사용합니다. Service마다 가상 서버를 만들고 엔드포인트를 실서버로 등록해 커널 해시 테이블 기반으로 라우팅합니다.

**특징**
- 해시 테이블 조회(O(1))라서 Service 수가 많아져도 성능이 거의 일정 — 대규모 클러스터에 유리
- `rr`(라운드로빈), `lc`(최소 연결), `dh`(destination hashing), `sh` 등 다양한 로드밸런싱 알고리즘 선택 가능
- 사전 조건: 커널에 IPVS 모듈(`ip_vs`, `ip_vs_rr` 등) 로드 필요, `ipset` 패키지 필요
- **strictARP 설정 필요** (특히 MetalLB L2 모드와 함께 쓸 때) — 안 하면 ARP 응답 충돌 발생 가능

```bash
# IPVS 관련 커널 모듈 확인
lsmod | grep ip_vs
# 없으면 로드
modprobe ip_vs ip_vs_rr ip_vs_wrr ip_vs_sh
```

**적합한 환경**: Service 수가 많은 대규모 클러스터, 트래픽 분산 알고리즘을 세밀하게 제어하고 싶을 때

## 참고: nftables 모드 (최신 대안)

Kubernetes 1.33부터 stable로 승격된 새 모드입니다. iptables의 순차 매칭 한계를 nftables의 set/map 자료구조로 해결해서, **IPVS와 비슷하거나 더 나은 성능**을 IPVS의 별도 커널 모듈 요구 없이 얻을 수 있습니다. `IPVS 모드는 1.35부터 deprecated` 되었고, `공식적으로 nftables가 IPVS의 후속 권장 모드`입니다.

지난번 부팅 로그에서 보셨던 `nft_compat` "unmaintained" 경고는 이것과는 결이 다른 얘기입니다 — `nft_compat`은 기존 iptables 명령어를 nftables 백엔드로 번역해주는 **호환 레이어**이고, kube-proxy의 nftables 모드는 이 호환 레이어 없이 nftables API를 **네이티브로 직접** 사용합니다. 즉 RHEL/Rocky의 방향성(iptables 계열 도구 정리)과 Kubernetes의 방향성(nftables 네이티브 모드 채택)이 같은 흐름 위에 있습니다.

## 비교 요약

|  | iptables | IPVS | nftables |
|---|---|---|---|
| 성능(대규모) | Service 많아지면 저하 | 일정함 | 일정함(IPVS와 동등 이상) |
| 로드밸런싱 알고리즘 | 랜덤만 | rr/lc/dh/sh 등 다양 | 랜덤 + 일부 개선 |
| 추가 커널 모듈 | 기본 내장 | ip_vs 계열 필요 | 기본 내장 |
| 현재 상태(1.35 기준) | 기본값, 계속 지원 | deprecated | 신규 권장 |

지금 쓰시는 클러스터가 Service 수가 적은 소규모라면 iptables(기본값) 유지해도 무방하고, 이왕 새로 세팅하는 거라면 nftables 모드를 검토해볼 만합니다.
