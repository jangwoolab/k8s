## 1. 쿠버네티스 주요 컴포넌트 6가지

클러스터는 **컨트롤 플레인**(두뇌)과 **워커 노드**(일손)로 나뉘며, 6가지 핵심 컴포넌트가 협력합니다.

```
┌─────────────── Control Plane ────────────────┐   ┌────────── Worker Node ──────────┐
│                                              │   │                                 │
│  kubectl ──▶ ① API Server ◀──▶ ② etcd       │   │  ⑤ Kubelet ──▶ 컨테이너 런타임    │
│                 ▲    ▲                       │   │       ▲        (Pod 실행)        │
│                 │    │                       │   │       │                          │
│      ③ Scheduler    ④ Controller Manager    │   │  ⑥ Kube-Proxy (Service 트래픽)   │
│      (어느 노드에?)   (상태를 원하는 대로)      │   │                                 │
└──────────────────────────────────────────────┘   └─────────────────────────────────┘
```

| # | 컴포넌트 | 위치 | 기능 | 작동 원리 (핵심) |
|---|---|---|---|---|
| ① | **kube-apiserver** | 컨트롤 플레인 | 클러스터의 **유일한 출입구**. 모든 요청(kubectl, 컴포넌트)의 인증·인가·검증 후 처리 | REST API 제공. 다른 컴포넌트는 서로 직접 통신하지 않고 **항상 API Server를 경유**. 상태 저장은 etcd에 위임 |
| ② | **etcd** | 컨트롤 플레인 | 클러스터의 **모든 상태를 저장**하는 분산 키-값 저장소 (단일 진실 공급원) | Raft 합의 알고리즘으로 다중 노드 간 일관성 유지. API Server만 etcd에 직접 접근 |
| ③ | **kube-scheduler** | 컨트롤 플레인 | 노드가 지정되지 않은 새 Pod를 **어느 노드에 배치할지 결정** | API Server를 감시(watch)하다 미배치 Pod 발견 → 필터링(자원·제약 조건) + 스코어링으로 최적 노드 선택 → 배치 결과를 API Server에 기록 |
| ④ | **kube-controller-manager** | 컨트롤 플레인 | 수십 개의 컨트롤러(ReplicaSet, Node, Job 등)를 실행해 **현재 상태를 원하는 상태로 수렴** | 각 컨트롤러가 조정 루프(2장)를 반복. 예: ReplicaSet 컨트롤러는 Pod 수가 부족하면 생성 요청 |
| ⑤ | **kubelet** | 모든 노드 | 노드의 에이전트. **자기 노드에 배정된 Pod를 실제로 실행·감시** | API Server를 watch해 자기 노드의 Pod 스펙 수신 → 컨테이너 런타임(containerd)에 실행 지시 → 상태·헬스를 API Server에 보고 |
| ⑥ | **kube-proxy** | 모든 노드 | **Service 트래픽을 실제 Pod로 전달**하는 네트워크 규칙 관리 | Service/EndpointSlice 변화를 watch → iptables/IPVS 규칙 갱신 → ClusterIP로 온 트래픽을 백엔드 Pod로 부하분산 |

**한 줄 요약 흐름** — `kubectl apply` → ① API Server 검증 → ② etcd 저장 → ④ 컨트롤러가 차이 감지·Pod 생성 → ③ 스케줄러가 노드 결정 → ⑤ Kubelet이 실행 → ⑥ Kube-Proxy가 트래픽 연결.

확인 명령:

```bash
kubectl get pods -n kube-system          # 컨트롤 플레인 컴포넌트 확인 (kubeadm 기준)
kubectl get componentstatuses            # (참고용, 일부 버전 deprecated)
kubectl describe node <노드명> | grep -A5 "System Info"
```

## 2. Controller 개요 — 조정 루프

Controller는 쿠버네티스 선언적 모델의 심장입니다.

```
        ┌───────────────────────────────────────┐
        │            조정 루프 (Reconciliation)   │
        │                                       │
   원하는 상태(Spec) ──┐                          │
        │             ▼                         │
        │        [ 차이 비교 ] ──차이 없음──▶ 대기  │
        │             │                         │
        │          차이 있음                      │
        │             ▼                         │
        │        [ 조치 실행 ] (Pod 생성/삭제 등)  │
        │             │                         │
   현재 상태(Status) ◀─┘        (무한 반복)       │
        └───────────────────────────────────────┘
```

- 사용자는 **"무엇을 원하는지(desired state)"**만 선언하고, **"어떻게 할지(how)"**는 컨트롤러가 담당합니다.
- 컨트롤러는 API Server를 **watch**하며 원하는 상태와 현재 상태의 차이를 끊임없이 좁힙니다.
- 이 구조 덕분에 장애 자동 복구(self-healing)가 가능합니다 — Pod가 죽으면 "3개여야 하는데 2개네?" → 즉시 재생성.

> **비유** — 온도를 "24도로 유지해줘"라고 설정하는 에어컨 서모스탯.
> 사용자는 목표만 정하고, 장치가 현재 온도를 측정해 계속 맞춥니다.

## 3. ReplicaSet

**ReplicaSet**은 "지정한 수(replicas)의 동일한 Pod가 항상 실행되도록" 보장하는 컨트롤러입니다.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3                 # 원하는 Pod 수
  selector:                   # 어떤 Pod를 관리할지 (라벨 매칭)
    matchLabels:
      app: web
  template:                   # 부족할 때 만들 Pod의 설계도
    metadata:
      labels:
        app: web              # selector와 일치해야 함
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

- **selector ↔ template.labels 일치**가 필수 — 불일치 시 생성이 거부됩니다.
- Pod를 지우면 즉시 다시 생성, replicas를 줄이면 초과분을 종료합니다.
- **하지만 실무에서 ReplicaSet을 직접 만들지 않습니다.** 이미지 변경(업데이트) 기능이 없기 때문입니다 → Deployment가 ReplicaSet을 관리합니다.

## 4. Deployment — 선언적 관리 · 롤링 업데이트 · 롤백 · 스케일

**Deployment**는 ReplicaSet의 상위 컨트롤러로, **버전 관리와 무중단 업데이트**를 제공합니다.

```
Deployment ──관리──▶ ReplicaSet(v2) ──관리──▶ Pod Pod Pod   ← 새 버전
                └──▶ ReplicaSet(v1) ──▶ (0개로 축소, 이력 보관)  ← 이전 버전
```

### 4.1 선언적 관리

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1             # 업데이트 중 초과 허용 Pod 수
      maxUnavailable: 0       # 업데이트 중 허용되는 불가용 Pod 수
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports: [{ containerPort: 80 }]
```

- `kubectl apply -f` 로 반복 적용 — 변경된 부분만 반영되는 **선언적 워크플로**.
- 이미지·환경변수 등 **template이 바뀔 때만** 새 ReplicaSet이 만들어집니다(replicas 변경은 롤아웃 아님).

### 4.2 롤링 업데이트

- 새 ReplicaSet을 점진적으로 늘리고 이전 것을 줄여 **무중단 교체**.
- `maxSurge` / `maxUnavailable` 로 교체 속도·가용성 균형을 제어.
- 진행 상황: `kubectl rollout status deployment/web`

### 4.3 롤백

- 이전 ReplicaSet들이 이력으로 남아 있어 즉시 복귀 가능.
- `kubectl rollout history` / `kubectl rollout undo [--to-revision=N]`
- 이력 개수는 `spec.revisionHistoryLimit` (기본 10)로 관리.

### 4.4 스케일

- `kubectl scale deployment web --replicas=5` 또는 매니페스트 수정 후 apply.

## [실습 1] Deployment 롤아웃 · 롤백 · 스케일

**목표**: 이미지 버전 변경 → 롤링 업데이트 관찰 → 문제 상황 롤백 → 스케일 조정.

### 1-1. Deployment 생성

```bash
# deployment를 사용해서 pod 배포
kubectl create deployment web --image=nginx:1.27 --replicas=3
```
```bash
# history 에 남김 : kubectl rollout history deployment/web
kubectl annotate deployment/web kubernetes.io/change-cause="update to nginx:1.27"
```

```bash
# 참고 
kubectl annotate rs/<레플리카셋 이름> kubernetes.io/change-cause="<기록할 내용>" --overwrite
```
```bash
# history 정보 출력
kubectl rollout history deployment/web
```
```bash
# 배포된 deployment에 LoadBalancer 부착
kubectl expose deployment web --type=LoadBalancer --port=80 --target-port=80
```
```bash
kubectl get deploy,rs,pod,svc -l app=web -o wide
```

> ✔ Deployment 1개, ReplicaSet 1개, Pod 3개가 보인다. RS 이름의 해시가 Pod 이름에 이어진다.

### 1-2. 롤링 업데이트 (이미지 변경)

```bash
# 새 터미널에서 변화 관찰
kubectl get pods -l app=web -w

# 이미지 업데이트 (change-cause 기록)
kubectl set image deployment/web nginx=nginx:1.29

# history 에 남김 : kubectl rollout history deployment/web
kubectl annotate deployment/web kubernetes.io/change-cause="update to nginx:1.29"

kubectl rollout status deployment/web        # 롤링 업데이트가 성공했는지 확인 명령어 
kubectl get rs -l app=web        # 새 RS 3개 / 이전 RS 0개
```

> ✔ 이전 Pod가 하나씩 Terminating 되며 새 Pod로 교체되는 과정을 -w 로 관찰했다.

> ✔ kubectl annotate deployment/web kubernetes.io/change-cause="update to nginx:1.29"

> ✔ Annotations 필드는 쿠버네티스 리소스에 임의의 키-값(Key-Value) 형태의 메타데이터를 부착해 부가 정보나 도구 설정 값을 기록하는 공간입니다. 식별이나 선택(Selector) 용도로 쓰이는 Label과 달리, 검색이나 그룹화에 사용되지 않습니다. [ kubectl describe deployment web ]에서 확인

### 1-3. 실패 상황과 롤백

```bash
# 존재하지 않는 태그로 잘못된 배포
kubectl set image deployment/web nginx=nginx:9.99
kubectl rollout status deployment/web --timeout=30s   # 진행 멈춤 확인
kubectl get pods -l app=web                            # ImagePullBackOff 확인

# 이력 확인 후 롤백
kubectl rollout history deployment/web

kubectl rollout undo deployment/web                    # 직전 버전으로
# 특정 리비전으로: kubectl rollout undo deployment/web --to-revision=1


kubectl rollout status deployment/web    # deployment "web" successfully rolled out


kubectl get pods -l app=web -o jsonpath='{.items[*].spec.containers[*].image}'; echo
```

> ✔ 잘못된 배포 중에도 기존 Pod가 유지되어 서비스가 죽지 않았다 (maxUnavailable 효과).
> ✔ undo 후 이미지가 nginx:1.29 로 복구되었다.

### 1-4. 스케일

```bash
kubectl scale deployment web --replicas=6
kubectl get pods -l app=web
kubectl scale deployment web --replicas=3
```

> ✔ replicas 변경은 rollout history 에 새 리비전을 만들지 않는다 — 왜일까? (template 불변)

### 1-5. 정리

```bash
kubectl delete deployment web
```

## 6. Service 개념 — 필요성 · 셀렉터 · ClusterIP · Endpoint · DNS

### 6.1 왜 Service가 필요한가

- Pod는 **언제든 죽고 다시 태어나며, 그때마다 IP가 바뀝니다** (롤링 업데이트·스케일·장애 복구).
- 호출하는 쪽이 Pod IP를 직접 알면 매번 갱신해야 함 → **고정된 접근 지점**이 필요.
- **Service = 라벨 셀렉터로 묶인 Pod 집합에 대한 고정 가상 IP + 부하분산 + DNS 이름.**

### 6.2 동작 구조

```
             ┌───────────── Service: web-svc ─────────────┐
 클라이언트 ──▶  ClusterIP 10.96.10.20:80  (고정 가상 IP)   │
             │        selector: app=web                   │
             └────────────────┬───────────────────────────┘
                              │  EndpointSlice (실시간 Pod 목록)
               ┌──────────────┼──────────────┐
               ▼              ▼              ▼
          Pod 10.244.1.5  Pod 10.244.2.7  Pod 10.244.3.2   ← IP가 바뀌어도
          (app=web)       (app=web)       (app=web)           자동 갱신
```

| 요소 | 설명 |
|---|---|
| **셀렉터(selector)** | `app=web` 라벨이 붙은 Pod를 자동으로 대상에 포함/제외 |
| **ClusterIP** | Service 생성 시 할당되는 클러스터 내부 고정 가상 IP (기본 유형) |
| **Endpoint(EndpointSlice)** | 셀렉터에 매칭된 "준비된(Ready)" Pod의 실제 IP:Port 목록 — 컨트롤러가 실시간 관리 |
| **kube-proxy** | ClusterIP로 온 트래픽을 EndpointSlice의 Pod들로 부하분산 (iptables/IPVS) |

### 6.3 클러스터 DNS

- CoreDNS가 모든 Service에 DNS 이름을 부여합니다.

```
<service>.<namespace>.svc.cluster.local
예) web-svc.default.svc.cluster.local
```

- 같은 네임스페이스에서는 `web-svc` 만으로, 다른 네임스페이스에서는 `web-svc.<ns>` 로 호출.
- 애플리케이션 설정에 IP 대신 **서비스 이름**을 쓰는 것이 표준입니다.

## 7. Service 유형 — NodePort · LoadBalancer · Headless · ExternalName

| 유형 | 접근 범위 | 동작 | 주 용도 |
|---|---|---|---|
| **ClusterIP** (기본) | 클러스터 내부 | 내부 고정 VIP + 부하분산 | 마이크로서비스 간 내부 통신 |
| **NodePort** | 외부 (노드IP:포트) | 모든 노드의 30000-32767 포트를 열어 ClusterIP로 전달 | 실습·온프렘 간단 노출 |
| **LoadBalancer** | 외부 (LB IP) | 클라우드 LB 자동 생성 → NodePort → ClusterIP 체인 | 클라우드 운영 표준 노출 |
| **Headless** (`clusterIP: None`) | 내부 | VIP 없이 DNS가 **Pod IP 목록**을 직접 반환 | StatefulSet, DB 개별 Pod 접근 |
| **ExternalName** | 내부 → 외부 | 클러스터 DNS가 외부 도메인의 **CNAME** 반환 | 외부 서비스(RDS 등)를 내부 이름으로 추상화 |

- 포트 용어: `port`(Service 포트) / `targetPort`(Pod 컨테이너 포트) / `nodePort`(노드 노출 포트).
- 계층 관계: **LoadBalancer ⊃ NodePort ⊃ ClusterIP** — 상위 유형은 하위 기능을 포함합니다.
- HTTP 경로/도메인 기반 라우팅과 TLS는 Service가 아닌 **Ingress/Gateway API**의 역할입니다(다음 차시).

## [실습 2] 서비스 노출

**목표**: ClusterIP → DNS 확인 → NodePort 외부 접속 → Headless 차이 관찰.

### 2-1. 대상 Deployment 준비

```bash
kubectl create deployment web --image=nginx:1.27 --replicas=3
```

### 2-2. ClusterIP + Endpoint 확인

```bash
kubectl expose deployment web --name=web-svc --port=80 --target-port=80
kubectl get svc web-svc
kubectl get endpointslices -l kubernetes.io/service-name=web-svc -o wide
```

> ✔ EndpointSlice에 Pod 3개의 IP가 보인다.
> ✔ Pod 하나를 삭제(`kubectl delete pod <이름>`)하면 목록이 새 Pod IP로 자동 갱신된다.

### 2-3. 클러스터 내부 접속 + DNS 확인

```bash
kubectl run client --rm -it --image=busybox:1.36 --restart=Never -- sh
# (컨테이너 안에서)
wget -qO- http://web-svc                 # 같은 네임스페이스: 짧은 이름
nslookup web-svc                          # ClusterIP 응답 확인
nslookup web-svc.default.svc.cluster.local
exit
```

> ✔ 서비스 이름만으로 nginx 응답을 받았고, DNS가 ClusterIP를 반환했다.

### 2-4. NodePort로 외부 노출

```bash
kubectl expose deployment web --name=web-np --port=80 --type=NodePort
kubectl get svc web-np                    # 예: 80:31234/TCP

# 노드 IP 확인 후 브라우저/curl 접속
kubectl get nodes -o wide
curl http://<노드IP>:<NodePort>
```

> ✔ 어느 노드 IP로 접속해도 응답한다 — kube-proxy가 모든 노드에 규칙을 만들기 때문.
> (클라우드 환경이면 `--type=LoadBalancer` 로 바꿔 EXTERNAL-IP 발급을 관찰)

### 2-5. Headless 비교

```bash
kubectl expose deployment web --name=web-hl --port=80 --cluster-ip=None
kubectl run client --rm -it --image=busybox:1.36 --restart=Never -- \
  nslookup web-hl
```

> ✔ 일반 Service와 달리 **Pod IP 3개가 A레코드로 직접** 반환된다.

### 2-6. 정리

```bash
kubectl delete svc web-svc web-np web-hl
kubectl delete deployment web
```

## 9. 정리

- **6대 컴포넌트**: API Server(출입구) · etcd(상태 저장) · Scheduler(배치) · Controller Manager(수렴) · Kubelet(실행) · Kube-Proxy(트래픽) — 모든 통신은 API Server를 경유한다.
- **Controller = 조정 루프**: 원하는 상태를 선언하면 차이를 스스로 좁힌다 (self-healing).
- **Deployment**가 ReplicaSet을 버전 단위로 관리 — 롤링 업데이트(maxSurge/maxUnavailable), `rollout undo` 롤백, `scale` 확장. replicas 변경은 새 리비전을 만들지 않는다.
- **Service**는 변하는 Pod IP 앞의 고정 접점 — 셀렉터 → EndpointSlice → kube-proxy 부하분산, CoreDNS 이름 제공.
- 유형 선택: 내부 통신 ClusterIP, 실습 노출 NodePort, 클라우드 운영 LoadBalancer, 개별 Pod DNS는 Headless, 외부 도메인 추상화는 ExternalName.

**다음 차시 예고** — Ingress(HTTP 라우팅·TLS), ConfigMap/Secret.
